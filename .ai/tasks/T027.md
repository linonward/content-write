## 用户结果

开发者修改业务规则时只需改一处：路由只处理 HTTP，业务规则集中在 service，数据访问使用 Drizzle 并受 schema 类型约束。改动 `schema.ts` 后，错误的列名或类型在 typecheck 阶段暴露，而不是运行时。用户可见行为不变。

## 背景

- `docs/product.md` 选定 Drizzle ORM，但 T008 起的 ideas、articles 与 worker 查询改为手写 SQL（约 148 处 `client.query`），只有 materials 部分查询使用 `getDb()`。手写查询的结果类型由泛型手动声明，与 schema 无关联。
- `repository.ts` 同时承担事务、加锁、前置条件判断和返回业务状态（如 `createArticle` 返回 `missing` / `stale`）。
- 文章来源是否仍为当前素材版本的检查在 `apps/api/src/modules/articles/repository.ts` 与 `apps/worker/src/outline-jobs.ts` 各实现一份。
- 每个事务手写 `BEGIN` / `ROLLBACK` / `COMMIT` / `release`。

约定见 `AGENTS.md` 与 `.ai/adr/003-api-layering.md`。

## 范围

- 按 `routes.ts` → `service.ts` → `repository.ts` 拆分 articles、ideas、materials 模块；`process.ts` 中的业务编排并入 service。
- repository 改用 Drizzle 查询构建器；行锁使用 `.for("update")` / `.for("update", { of: ... })`；Drizzle 无法表达的查询用 `sql` 模板并引用 schema 列。
- 事务改用 `getDb().transaction()`，由 service 开启并把 `tx` 传给 repository。
- service 抛出领域错误；路由或 `app.onError` 将其映射为统一错误响应，替代 repository 返回的状态字符串。
- api 与 worker 共用的规则（来源版本检查等）移入共享包，两侧调用同一实现。

## 不包括

- 修改接口路径、请求或响应结构、错误码、HTTP 状态码。

- worker 任务领取（`FOR UPDATE SKIP LOCKED`）以外的队列语义调整。

## T027a 实施记录

- articles 拆为 `routes.ts`（校验与错误映射）、`service.ts`（规则、事务、`ArticleError`）、`repository.ts`（Drizzle 查询，接收 `tx`）。`listArticles` 无业务规则，由路由直接调用 repository。
- 新增 `@content-write/db/article-sources`：`readArticleSources`、`sourcesIntact`、`citesOnlySourceEvidence`，api 的生成、保存、确认与 worker 的加载、完成共用。
- 偏离原范围：`ai-jobs/queue.ts` 改为接收 Drizzle 执行器，文章入队才能与文章行锁处于同一事务。ideas、materials 的 `process.ts` 暂以 `fromClient(client)` 包装原 pg 事务，各加 3 行，T027b/c 迁移时删除。worker 新增依赖 `drizzle-orm@0.45.3`（与 db 包同版本）。
- 规则统一带来的行为收紧：生成、保存、确认大纲时，来源都必须存在修订标题和整理摘要（原先生成只要求整理记录存在、确认只核对来源数量）。正常数据下整理结果总含摘要，因此用户可见行为不变；以前在 worker 阶段才变为 stale 的异常数据，现在在 API 就返回 `ARTICLE_SOURCES_MISSING`。
- 幂等哈希保留原字段名 `material_id`、`material_version`，T027 前入队的请求重试仍匹配原任务。
